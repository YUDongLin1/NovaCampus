==================== 第 1 步:apply(拆掉炸点)====================

$ python docs/p4f/patch_check_c5_tripwire.py apply

  换句话说:第一版的自测在这条路径上不是「会红」,而是「会扣钱」。

==================== 结论 ====================

1. 拆掉流式炸点 → 134/136、退出码 1,且红项正是 C5 A / C5 B(不是别的用例连坐)。
2. 复原后→ 136/136、退出码 0。**这两个数字必须成对出现**,单看全绿说明不了拦截力(坑 52)。
3. C5 组共 12 条,四组断言:
   A  流式炸点在位(直接 async for 一次,必须抛 LlmCalled)
   B  短路被拆掉后走 HTTP 流式端点,必须撞炸点而不是发真请求
   C  短路完好时同一条请求零LLM;并用「会产事件的替身」反向对照,
      证明 C 组不是靠「端点根本不调 chat_stream_for」假绿
   D  install_llm_probe 的复位函数有效(比__func__/__self__,不比 bound method 对象)

⚠️ 一条被这套自测抓出来的**认知修正**(不是被测代码的缺陷):
   「短路完好时零 LLM」**不是全局性质**,它成立的范围仅限 C4 走过的那几条确定性分支。
   我第一版拿「无 persona、不指定 scope」的请求去断言它,当场两条红 —— 那条请求
   本来就该走 LLM(库里无文档 → pre 三个来源全为 None)。
   尺子的前提写错了,不是被测代码错(坑 52 的隐蔽形态:断言红了,但红的理由不对)。
