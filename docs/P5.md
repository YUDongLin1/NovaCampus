## 二、现状与目标

**现状**（P4f 之后）：`<main>` = `aside#conv-sidebar`（新会话 / persona 下拉 / 会话列表 / 归档 / 账户入口）

问题：知识库、周报、工作记录被塞在右侧抽屉里，**入口层级低于它们实际的重要度**；
「辅导员（人设）」只有一个下拉框，**看不到已设定的人物、没有形象、没有管理入口**。

**目标壳层**：

## 三、逐入口规格

### 3.1 新会话
- 点击 → 主区切到会话页、清空当前会话、**不立刻建会话**（沿用现有「首条消息时自动建会话」的行为，
  避免留下空会话污染列表 —— 这是 P2 期就有的约定，别改）。
- 断言：连点三次「新会话」后 `conversations` 计数**不变**。

### 3.2 历史对话
- 左栏下半区，按 `updated_at` 倒序；分组标题「今天 / 近 7 天 / 更早」。
- 每条显示：标题、**人设徽标**（`persona_name`，P4f 已回传）、消息数、归档态。
- 顶部一个「显示归档」开关（沿用现有 `#conv-arch` 语义，不改行为）。
- 断言：分组边界用**服务端时间**判定，不得用浏览器本地时区（演示机时区差异会假红）。

### 3.3 知识库
- 把现在右侧抽屉的 `#pane-kb` 整体提升为主区一页：**左树（文件夹）+ 右表（文档）**两栏布局，
  不再挤在 331px 的抽屉里（P4f 走查实测：窄视口下 `可见/分类/学段` 三个下拉被压到 51px，几乎不可读）。
- 上传/导入/新建文件夹/移动/删除 全部沿用现有接口与权限，**不改语义**。
- 断言：`document/folder` 的 RBAC 与 `role_min` 口径**逐条不变**（P4c 的三条硬约束必须仍成立，
  用 P4c 那五条安全探针复跑，不许因为改版而弱化）。

### 3.4 辅导员（人设）——**本单的核心新页面**
列表态：
- 卡片网格（每行 3–4 张，最小 260px），每张卡：
  **头像**、名称、学院、风格标签、绑定范围摘要（「绑定 2 个文件夹 / 全库」）、
  可见性（`private`→「仅自己」、`public`→「全校可用」）、`默认` 角标、当前会话使用中的高亮。
- 顶部：`+ 新建人设`、搜索框（按名称/学院过滤，**纯前端过滤**，不发请求）。
- 学生看到的：只有 `public` 人设卡（后端已脱敏，见 P4f 第 3 回 ②），
  卡上只有「**用这个人设开会话**」按钮，**没有**编辑/删除。

详情/编辑态（辅导员与 admin）：
- 表单字段沿用 `POST/PATCH /api/personas`：名称、学院、风格（`detailed/concise/warm/formal/balanced`）、
  `persona_prompt`、绑定文件夹（多选，走 `/api/kb/folders` 列表）、绑定分类、可见性、设为默认。
- **头像选择器**：从内置库里选（见 3.5），选中值存进 persona 的 `style` 之外的新字段
  `avatar`（**需要一次后端小改**：`personas` 加 `avatar TEXT DEFAULT ''` 列，
  走既有 `_migrate()` 的幂等加列，**不得**要求重建库）。
- 删除 = 软删（`deleted_at`），历史会话保留并显示「人设已删除」徽标（P4f 已实现，别改）。

只读态（学生）：点卡片进详情页，**全部字段只读**，`persona_prompt` 不显示（后端已不下发，前端也不要有占位提示语）。

### 3.5 内置头像库
- **数量**：16 个（8 中性 + 4 偏女性 + 4 偏男性表述，避免刻板印象：以「配色/发型/配饰」区分，不用职业/性别绑定）。
- **形态**：内联 SVG（`<symbol>` 雪碧图或 `mask-image`），**不引入任何外部字体/图片/CDN**；
  单个 ≤ 2KB，总增量 ≤ 40KB。
- **标识**：`avatar` 存**逻辑 id**（如 `av-07`），**不存文件路径、不存 base64** —— 渲染时前端按 id 映射到内联符号，
  将来换图不迁移数据。
- **红线**：不得出现真实人物形象；不得使用校徽/校名图形（商标与身份风险）；
  不得引入任何真实学工数据或照片。

### 3.6 周报 / 工作记录
- 各自主区一页，内容沿用 `#pane-weekly` / `#pane-records` 的现有 DOM 与接口。
- 学生不可见（入口不渲染 + 后端仍 403 双保险）。

### 2. 三个「故意保留旧名」的决定（不是忘了改）

改版最容易犯的错是**顺手改名把别人的断言变成静默不判**。所以：
- `aside#conv-sidebar` —— 左栏升级成导航轨，但 P4f 契约自测按这个 id 断言「账户入口在栏内」；
- `pane-kb` / `pane-records` / `pane-weekly` —— 内容原样搬进主区，类名仍是 `.tabpane`
  （行的还是同一套 `.tabpane.active` 的显示/隐藏机制，不另写一套 display 判据）；
- `switchTab()` —— 机制没变（仍是切主区那一页），保留名字以免既有调用点与契约断言失效。

**结果**：P4f 的前端契约自测**不用改判据就仍然全绿**（99 → 107，增量全部来自新增的
css/js/pf-* 表单 id 被同一套断言展开覆盖）。

### 5. 截图暴露并修掉的两处真布局缺陷（本单 `web/**` 在白名单内）

1. **`#acct-entry` 完全没有 CSS**（截图实测与历史列表 `li` 交集 **0.80**，两档都复现）。
   根因：theme.css 里账户卡的样式全部挂在 **`#account-card`** 这个选择器下、
   且是 `position:fixed; right:20px; bottom:20px`（P4f 时代的右下角浮层）；
   P5 把它搬进左栏、改名 `acct-entry` 后那些规则**一条都不再命中**，
   `.avatar` 于是掉进全局 52px 圆形规则，糊在列表上。
   **修法**：在 `shell.css` 里补回布局（`theme.css` 一行未动，符合 P5 §5）。
2. **上传解析行三个下拉被压成 51px 窄条**（`theme.css` 的 `.row input, .row select {flex:1}`
   让 5 个控件平分，而 `input[type=file]` 固有宽度远大于 select）。
   **这就是 P4f 走查记的那个坑**，搬进主区后依然存在。
   **修法**：文件选择器 `flex:0 1 240px`、三个下拉 `flex:0 1 auto; min-width:92px`。
   **实测 51px → 92~96px**（两档视口一致）。

### 7. ⚠ 新发现：与 P5 无关的既有架构缺陷（**不在本单修，如实交回**）

真浏览器走查时出现 `enter()` 卡死在 `await loadHistory()`，追到根因：

```
main.py:48  current_user  →  db.py:424  user_by_token
sqlite3.InterfaceError: bad parameter or other API misuse
```

**根因**：`db.py` 用单例 `_conn` + `check_same_thread=False`，而 FastAPI 的 `Depends`
经 `anyio.run_in_threadpool` 在**多个工作线程**里调用它。读函数一律不加 `_lock`
（实测**31 个**读 `_conn` 的函数全部无锁，含 `user_by_token` / `list_conversations`）。
同一 `sqlite3.Connection` 被多线程同时 `execute` 就抛 `InterfaceError`，
且该异常把连接打入**持久错误态** → 之后所有请求挂起（前端表现为整页半瘫）。

**逐步排除**（每一步都排掉一种可能）：
1. SQL 层直跑正常 —— 学生 `user_id=3` 返回 200 行、耗时 <0.1s（**不是慢查询**）；
2. `sessions` 数据正常 —— student's 318 条 token 长度均 32，JOIN 可命中；
3. 换干净进程仍复现 —— `:8985` 杀净后起 `:8986`，单发即挂；
4. 单发也挂 —— 并发不是必要条件（但进程内此前发生过并发）；
5. 服务端栈顶定位到 `db.py:424`。

**影响面**：这是**既有架构缺陷**，与 P5 无关；第 1 回未记录是因为当时只有单请求 curl，
没有并发。第 1 回那条「静态资源全 200 = 页面不会静默半瘫」的替代自查**不足以覆盖它** ——
资源都在，是后端连接先坏了。

**为什么本单不修**：① 开单「禁改」明确含 `novaagent/novaagent/**`，`db.py` 正在其中；
② 这是架构级改动（连接池 / 线程局部连接 / 读路径统一加锁），不该混进一个前端单，
混进去等于让一个前端单的 diff 里藏着一处连接模型变更 —— 那正是最难复验的一类改动。

**处置**：证据 `p5r2_browser_walkthrough.txt` 第 3 节；已记入 `docs/TASKS.md` 技术债。
**需要 Qoder 决定是否开单。** 我的建议：单独开一张「db 连接并发安全」的单，
先加读路径 `_lock`（最小改动、立刻止血），再评估是否换线程局部连接。
