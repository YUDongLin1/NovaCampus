> 进而可能去改评测用例（把 qa-12 改绿），那会掩盖真实缺陷。现已修法正确、只删缓存。

离线对、端到端红 —— 第一反应会是「C0-① 修法没修好」。

## 二、真正的破案线索：**trace 里少了一个字段**

评测报告 `reports/eval_report_20260930_194314.json` 的 `last_context.retrieval_trace`：

```json
{"node":"retrieve","ms":1096,"n_sources":3,
 "top_score":0.966,"n_above_threshold":7,
 "fused_candidates":8}          ← ① 值是 8，不是 12
```

两个硬矛盾：

| 观测 | 说明 |
|---|---|
| `fused_candidates: 8` | 服务端跑的是 **8 槽**，不是改后的 12 槽 |
| **缺 `fused_candidate_docs`** | 这个字段是**本次 C0 新增**的；trace 里根本没有 |

第二个是决定性的：**新加的字段不可能"恰好没触发"** —— 只可能是**加载了旧字节码**。

时间戳对得上：

```
rag.py                     19:18:49   ← 评测启动时刻
__pycache__/rag.cpython-312.pyc  19:18:49
```

## 三、还有一个**必须一起修**的问题：重复定义

`rag.py` 常量区当时是：

```python
FUSION_TOP_K = 8                      # ← 第 19 行，T10 遗留
...
FUSION_TOP_K = int(config.env("NOVA_FUSION_TOP_K", "12"))   # ← 第 40 行，P4e C0-①
```

Python 顺序执行，**后者生效**，所以静态读代码会以为「8 早被覆盖了，没事」。
但它有两个害处：
1. 让人误判生效值（我一度就是这么读错的）；
2. 只要有任何执行路径在第 40 行之前 import 到 `rag`，拿到的就是 8。

已**删除第 19 行**，并在原位留下注释说明，禁止再加同名模块级常量（坑 52 同源）。

## 五、纪律教训（比修法本身重要）

1. **「离线探针绿 / 端到端红」时，先怀疑加载的是旧代码，不是修法错。**
   判别法：**看 trace/响应里有没有"本次新增的字段"**。新字段缺失 = 100% 旧代码，比任何数值推断都硬。
2. **整轮评测是稀缺资源**（本单明文规定"唯一一次"）。首轮跑出与离线矛盾的结论时，
   **先花 2 分钟做一次单请求端到端复验**再决定是否重跑整轮 —— 我这次首轮直接重跑整轮，
   属于流程上可以更省的一次。
3. **改完代码先删 `__pycache__`**，尤其在 Windows + venv + 多 Python 版本
   （本机同时有 cpython-312/313/314 三份 `.pyc`，更容易撞）。
4. **重复的模块级常量必须删干净**，别指望"后定义的覆盖前面的"—— 它会让读代码的人做出错误判断。
