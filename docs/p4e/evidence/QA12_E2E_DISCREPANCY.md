## 一、真因一：`run_with_server.sh` 不透传 `--base`，评测一直打在 `:8900` 旧进程

### 现象

前 6 轮整轮评测，`qa-12` **全部** `TOTAL 47/48`、`fused_candidates: 8`、**缺** `fused_candidate_docs`。
而我在同一份代码上离线直连与手动端到端**稳定复现为 PASS**：

```
(sources, fused_candidates, fused_candidate_docs) → 次数
   (4, 12, 4) → 12          ← 手动 12/12 全部如此，判红 0 次
```

`rag.py` 只剩一处 `^FUSION_TOP_K`（= 12）、`graph.py` 含新字段、site-packages 无旧包、
父 shell 无 `NOVA_FUSION_TOP_K`、venv 与 uv 是**同一解释器**（`pyvenv.cfg.home` 指向 uv cpython-3.12）、
`__pycache__` 已清 —— **全部排除**。

### 决定性证据

`run_evals.py` 第 42 行 `BASE = "http://127.0.0.1:8900"`（模块级默认），第 629 行 `--base` 可覆盖。
而 `docs/p4d/run_with_server.sh` 起服务的写法是：

```bash
.venv/Scripts/python.exe "$REL" "$@"     # 只透传 "$@"
```

我传的是 `../evals/run_evals.py`（**没带 `--base`**），于是 `BASE` 保持默认 `:8900`，
**评测从头到尾连的都是 `:8900` —— 我在 `:8902` 辛苦起的新服务，评测根本没连。**

而 `:8900` 是**他人于 15:40:54 启动的常驻实例**（`Get-CimInstance` 实测
`CreationDate 09/30/2026 15:40:54`，PID 34984/41956），
加载的是 **15:40 时的代码**（`FUSION_TOP_K` 改动前）→ 一切现象全部对上。

直接打 `:8900` 验证：

```
【:8900 常驻实例（他人 15:40 启动）】
  n_sources = 3
  fused_candidates = 8
  fused_candidate_docs = None
  trace 键 = ['fused_candidates','ms','n_above_threshold','n_sources','node','query','top_score']
```

与评测报告里的值**逐字一致**。

另有一个佐证：在第六轮评测**运行期间**打 `:8902`（新代码），得到 `fused=12 / docs=4 / n_sources=4`，
与同一轮报告的 `fused=8 / None / 3` 并存 —— 同一时刻两个端口两种结果，只能是"打错端口"。

### 正确跑法与结果

```bash
bash docs/p4d/run_with_server.sh 8902 ../evals/run_evals.py --base http://127.0.0.1:8902
```

→ `qa-12` **PASS**：`命中 ['奖助学金'], 引用 4 条 | R@k=1.0 忠实度=1.0(llm)`。

**C0-① 修法完全成立**：`qa-12` 从 R@k 0.0 → 1.0、目标块进来源第 4 位（0.5822）。

### 教训（建议写进 `run_with_server.sh`）

**helper 必须透传 `--base`**，否则它起的服务与评测连的端口不一致，
会造出"代码改了但评测没生效"的**假红**，极易被误判成修法失败而去改用例（违反坑 39/52）。
建议在该脚本里加一行自检：

```bash
if [[ "$REL" == *run_evals.py* && "$*" != *--base* ]]; then
  echo "[FATAL] 评测未指定 --base，将回落到默认 :8900（很可能是他人的常驻旧实例）"; exit 3
fi
```

⚠ 我**没有改** `docs/p4d/run_with_server.sh`（不在本单白名单），只在此建议。

## 二、真因二：`qa-17` 是**生成侧偶发省略正文**（答案形态抖动，**不是判据问题**）

前 6 轮它全 PASS —— 同样是**因为评测打在 `:8900` 旧实例**（8 槽）。
正确 12 槽下（`:8907`）连测 10 次曾测得 `PASS = 2/10`，
本轮在 `:8902`（同一份代码、同一 12 槽）用 `probe_qa17_answer.py` 复测 5 次得 **`FAIL = 2/5`**。
**两次测量的失败比例不一致（8/10 vs 2/5）本身就是证据：这不是稳定结构，是生成抖动。**

### 复测证据（`docs/p4e/evidence/qa17_answer.json`，问句取自 `cases.json`，未手写）

```
[1/5] len=41  src=2 marks=[未在知识库,请以,以研究生主管部门] refs=[]    digits=[]                FAIL
[2/5] len=323 src=2 marks=[...] refs=['1'] digits=[2025,13,1,2025,2026]  PASS
[3/5] len=354 src=2 marks=[...] refs=[]    digits=[2025,13,2025,2026]     PASS
[4/5] len=156 src=2 marks=[...] refs=[]    digits=[]                       FAIL
[5/5] len=333 src=2 marks=[...] refs=['1'] digits=[2025,13,1,2025,2026]  PASS

R@k 全 1.0 = True | 来源全对 = True（5/5）
```

**检索侧完全正常**：5/5 `R@k=1.0`、5/5 来源为 doc77《本科生荣誉称号评审管理办法》。
**红点 100% 在生成侧**：模型有时把答案写成「学段声明 + 免责」而**不复述正文条款**。

### 关键：两次 FAIL 的形态确实是「非答案」，判据判对了

`#1`（全文 41 字，**零引用零数字**）：

```
以下依据本科生办法，研究生相关规定未在知识库覆盖，请以研究生主管部门最新通知为准。
```

→ **完全没有回答"能否兼得"**。学段声明做了，但没有实质内容。这**就是**非答案。

`#4`（全文 156 字，零引用零数字）：

```
以下依据本科生办法，但需特别说明：研究生荣誉称号评审办法未在知识库中覆盖。
因此，关于研究生是否可同时获得两个及以上荣誉的问题，知识库中暂无相关内容。
建议以研究生主管部门（如研究生院或党委研究生工作部）发布的最新通知为准，
或查阅《西南交通大学研究生荣誉称号评审管理办法》等专门文件获取准确信息。
```

→ 同样**没有给出本科生兼得条款的内容**，等于没回答问题。

而 3 次 PASS 都实打实引用了条款（`〔2025〕13号` 第二十一条 + `[1]` 角标），
并明确「该规定仅适用于本科生，不适用于研究生」。

**结论：判据没有误杀。** 判红时答案确实是非答案（`substantive_len` 剥离免责后归 0、
零 `[n]` 零数字），判绿时答案确实有实质条款。**判据行为正确，是生成侧不稳定。**

⚠ 我**更正**本节早先的判断：此前写「12 槽把 doc77 第 3+ 块多召进来 → 答案形态变了 → 连带影响」，
并称 8/10 是「稳定失败非抖动」。**该归因不成立**——重测显示失败率本身会变（8/10 → 2/5），
且 PASS/FAIL 的分野是**是否复述正文条款**，与召回数无关。真正的机制是生成侧偶发偷懒。

### 待裁决（我未擅自改）

| 选项 | 做法 | 风险 / 代价 |
|---|---|---|
| **A** | 放宽判据（如「免责句不算非答案」或「实质 > 0 即放行」） | ❌ **不可接受**：上表两次 FAIL 是真非答案，放宽即放过它们，与坑 39/52 冲突（削弱检测力换假绿） |
