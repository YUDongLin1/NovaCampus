核心设计 · 四层防线

把「不要瞎编」从提示词
下沉为代码约束

大模型答政策问题最大的风险不是「答不出」，而是答错了还很自信。 这四层不是 prompt 里的叮嘱，是可单测、可复现、可被评测打分的代码路径。

为什么「措辞」会决定成败

  • 同一件事，用户有 8 种问法，纯字面匹配只命中 3 种。
  • 加上意图判定 + 召回不达标自动改写后，实测 8/8 命中。
  • 上下文占用超过窗口 65% 时，按主题压缩较早内容再注入，多轮不丢关键约束。
  • 提问时用 @ 指定本次检索范围（文件夹多选），把「问哪一份文件」交给用户。
  • 评测时把温度压到 0（NOVAAGENT_EVAL_TEMPERATURE），保证分数可复现。

案例研究 · 最有价值的一份文档

一个 26 用例全过、拒答准确率 1.0、忠实度 1.0 的 RAG 系统， 被一线辅导员的三个真实学生提问当场打回原形。

而所有指标对此完全失明。这份 docs/CASE_STUDY.md 记录的是「发现 → 量化归因 → 反向改造验收标准」的全过程， 过程中还证伪了作者自己先前提出的两个解释。文中数字全部可复现。

看它如何改造评测集 →
失守

知识库里没有，它照样答，还标了引用编号。 sources = []（零来源）却给出 5 步办理流程、材料清单、具体 APP 名称，句末标注 [1]——一个不存在的引用。

归因

失守不随机。6 个问法的对照实验显示：与问句的情境丰富度正相关—— 越像真实用户会打的字，越容易被模型当成「可回答的通用问题」。

证伪

为什么指标看不见？6 条 refusal 用例全是「今天天气怎么样」「微信的创始人是谁」这类 域外问题。真正危险的「校园域内、但库里恰好没有」，一条用例都没有——所以拒答准确率长期 1.0。

改造

不是加 prompt 规则，而是补评测集与验收项。 新增 refusal_indomain 6 条 + 追问拒答、历史假前提、多轮、上下文压缩等用例，把结论反向写进验收标准。
